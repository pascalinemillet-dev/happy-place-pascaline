- Store application roles in `allowed_user_roles`, separate from the email whitelist, to prevent privilege escalation.
- Scope manager review permissions through `manager_teams`, because one manager may oversee multiple teams.
- Render company identity through the shared `BrandHeader` so every user-facing page stays consistently branded.
- Generate personal submission reports in the browser from RLS-scoped queries so exports never exceed the signed-in user's access.
- After any migration that touches an ENUM, a trigger, or a status-related function, run `select * from private.run_smoke_tests();` — every row must come back with ok = true.

- Load heavy browser-only libraries (ExcelJS, JSZip) from `public/vendor` via `loadBrowserLib`, never `import()` them: bundling their Node dependencies into the server crashes the published site on every page.
- News images live in the private `news-media` bucket at `{news_id}/{uuid}.{ext}`; storage write rights mirror news edit rights via `private.can_edit_news_media`, and the app removes old files itself (before deleting the row) because storage objects cannot be deleted from SQL.
- Keep metric delta and value formatting in shared dashboard helpers so management rows and dashboard trends interpret numeric text consistently.

- Connexion réservée à la liste blanche (lot 0) : seules les adresses de `allowed_users` peuvent créer un compte (trigger `private.refuser_compte_non_invite` sur `auth.users`), et le rôle vient de `allowed_user_roles`, attribué par un admin. `public.choisir_mon_role` est désactivée : ne pas la réactiver.
- F1 « Signaler un point bloquant » : une soumission est une idée ou un point bloquant (`submissions.kind`). Un point bloquant se publie uniquement par `public.publish_blocker_submission` (statut OUVERT, pôle du référentiel `teams`), jamais par une écriture directe dans `blockers`. Les appels à l'IA passent par les fonctions serveur de `src/lib/ai.functions.ts`, qui lisent les données sous l'identité de l'utilisateur (RLS) puis appellent le webhook Make « HappyPlace - IA » ; c'est Make qui appelle OpenAI. Jamais de clé dans le navigateur, jamais de nom ni d'e-mail d'auteur dans les appels à l'IA (scénario Make « HappyPlace - IA »). Les consignes (prompts) restent dans ce fichier.
- US68 : une soumission refusée se modifie et se renvoie uniquement par `public.resubmit_submission`, et s'archive uniquement par `public.archive_submission`. L'auteur n'a aucun droit d'écriture directe sur `submissions`. Le renvoi garde l'identifiant, repasse « en attente », efface le motif (il reste dans `submission_status_history`) et relance l'e-mail US60 ou US62, signalé « renvoyé après refus ».
- US71 : `public.publish_blocker_submission` accepte une description reformulée (`_description`, facultative) ; elle part dans `blockers.description`, la soumission garde le texte de l'auteur.
- Soumission de l'admin (2026-11-04) : l'admin choisit l'équipe concernée, obligatoire, parmi les équipes non réservées de `teams` (trigger `private.set_submission_owner`) ; la soumission suit le circuit de cette équipe. Personne ne valide, ne refuse ni ne publie sa propre soumission (`private.peut_decider_soumission`, contrôlée dans `private.enforce_submission_review` et `public.publish_blocker_submission`), sauf l'admin auteur quand l'équipe n'a aucun manager inscrit. L'interface applique la même règle avec `canDecide` (`src/lib/f1.ts`).
- US64 révisée : « M'envoyer par e-mail » du récap passe par `public.send_team_recap_email` (manager seulement, destinataire = le manager connecté, 10 envois par heure au plus), qui écrit dans `public.notifications` avec l'événement `recap_point_equipe`. Exception décidée par Pascaline le 2026-11-03 à la règle « ni description dans les e-mails » : le récap porte des titres, des phrases de l'IA et, sans IA, des débuts de description.
